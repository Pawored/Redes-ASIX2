# DNS — Servicios en Red

> Apuntes basados en la presentación *1.1-DNS1.pptx*

## 1. ¿Qué es el DNS?

El **DNS (Domain Name System)** traduce nombres de dominio (fáciles de recordar para las personas) en direcciones IP (las que usan las máquinas para comunicarse).

- Cuando un usuario accede a un sitio web, se ejecutan una serie de peticiones internas que acaban traduciendo el nombre de la página a la dirección IP del servidor donde se aloja.
  - Ejemplo: `www.ifp.es` → IP `213.192.253.78`
- Es una **base de datos distribuida** con información sobre hosts y servicios.
  - Permite un **control local** de los "segmentos" de la base de datos.
  - Cada segmento es accesible a toda la red mediante un esquema **cliente-servidor**.
- Alcanza **robustez y rendimiento** gracias a la **replicación** y el **caching**.

## 2. Un poco de historia

- En los años **80** se creó el sistema de nombres de dominio, sustituyendo al método anterior basado en el archivo local **hosts**, muy propenso a errores.
- El archivo `hosts` todavía existe hoy en día:
  - **UNIX/Linux:** `/etc/hosts`
  - **Windows:** `%SystemRoot%\system32\drivers\etc\hosts`
- El DNS comenzó a popularizarse a **finales de los años 90**.

## 3. DNS y el modelo OSI

- El servicio DNS se sitúa en la **capa de aplicación** del modelo OSI (la capa más cercana al usuario, junto a SMTP y HTTP).
- Emplea la capa de transporte:
  - **UDP** — normalmente, para las peticiones.
  - **TCP** — solo si el tamaño de la respuesta supera los **512 bytes**.
- Usa el **puerto 53**.
- Está definido en varios RFC del IETF; el más actual es el **RFC 6895**.

## 4. Ventajas del DNS frente al fichero hosts

- Elimina los problemas del sistema basado en `HOSTS.TXT` (mantenimiento manual, no escalable).
- Al ser **jerárquico**, el espacio de nombres permite **particionar** y gestionar los subdominios de forma independiente.
- Resuelve el problema de **colisiones o nombres duplicados**: garantiza que todos los nodos hermanos/hijos de un mismo nodo tengan etiquetas distintas.
  - No puede haber dos nodos con el mismo **FQDN**, aunque sí pueden compartir etiqueta sin ambigüedad (ej: `www.upc.edu`, `www.fib.upc.edu`, `www.eetac.upc.edu`).

## 5. Proceso de una petición DNS

1. El cliente (navegador, programa de correo) introduce una URL.
2. Se realiza una petición al **resolver**.
3. El resolver **almacena en caché** direcciones IP ya solicitadas anteriormente y las proporciona directamente si las tiene.
4. Si la IP no está en la caché del resolver, la petición se redirige al **servidor DNS correspondiente** (normalmente el del proveedor de Internet).

## 6. Tipos de servidores DNS

Existen **4 categorías** de servidores DNS:

| Servidor | Función | Analogía |
|---|---|---|
| **Solucionador recursivo** (resolver) | Recibe las consultas de los clientes | Bibliotecario |
| **Servidores de nombres raíz** | Los 13 servidores raíz principales a nivel mundial | Índice de libros de una biblioteca |
| **Servidores de nombres TLD** | Ej: `.com`, `.net`, `.edu` | Estantería de libros |
| **Servidores de nombres autoritativos** | Contienen el registro **SOA** | Diccionario en la estantería (definición concreta de un nombre) |

### Solucionador recursivo vs. Servidor autoritativo

- Cada uno desempeña un papel diferente y se sitúa en un punto distinto del proceso de consulta.
  - **Solucionador recursivo:** está al **inicio** de la consulta. Es el equipo que responde a la solicitud del cliente y dedica tiempo a localizar el registro DNS, haciendo peticiones sucesivas hasta llegar al servidor autoritativo (o hasta devolver un error si no existe). Gracias a la caché, no siempre necesita hacer varias peticiones.
  - **Servidor autoritativo (SOA):** está al **final** de la cadena. Contiene realmente los registros de recursos DNS y responde con el registro solicitado. Puede responder con sus propios datos sin consultar a nadie más: es la **fuente final de verdad**.

## 7. Tipos de consultas/peticiones DNS

Cuando un servidor DNS no puede responder con la información de su propia base de datos, puede realizar dos tipos de consultas:

### Recursiva
- El servidor DNS que la recibe **siempre** devuelve una respuesta (o un error).
- Si es necesario, consulta a otros servidores (que a su vez pueden hacer consultas recursivas o iterativas).
- **Para el cliente:** cómodo, ya que solo espera mientras el servidor recorre el árbol DNS.
- **Para el servidor:** costoso, por lo que a veces se niega a aceptar este tipo de consultas.

### Iterativa
- El servidor que recibe la petición da la información si la conoce; si no, indica en qué otro servidor puede encontrarse (envía una referencia con un **RR de tipo NS** apuntando al servidor de nombres "más cercano" a la respuesta).
- El **cliente** es quien debe seguir esas referencias.

### Resumen de los 3 roles en una resolución

| Rol | Respuesta | Información | Comportamiento |
|---|---|---|---|
| **Autoritativo** | Brinda respuesta directa | La tiene en su propia base de datos local | No tiene autoridad sobre otros dominios |
| **Recursivo** | Brinda la info al cliente | Si no la tiene, consulta recursivamente a otros servidores hasta encontrar una respuesta autoritativa | Intermediario entre cliente y jerarquía DNS |
| **Iterativo** | Brinda respuesta parcial | Indica al cliente dónde buscar el resto de la información | Delega la siguiente consulta al cliente |

## 8. Espacio de nombres del DNS

- Utiliza un **espacio de nombres jerárquico**, en forma de **árbol**, con un **nodo raíz (root)**.
- Cada nodo tiene una **etiqueta**; la etiqueta de la raíz es un **punto (`.`)**.
- El **FQDN (Fully-Qualified Domain Name)** de un nodo puede ser relativo o absoluto, y es la **concatenación de etiquetas** desde el nodo hasta la raíz.

Ejemplo: `www.ejemplo.com.`

| Parte | Significado |
|---|---|
| `www` | Nombre del host (subdominio) |
| `ejemplo` | Dominio de segundo nivel |
| `.com` | Dominio de nivel superior (TLD) |
| `.` (final) | Raíz del DNS (se suele omitir, pero existe en la jerarquía) |

### Niveles

- **Top-Level Domains (TLD):** nodos justo debajo de la raíz. Suelen indicar el tipo de entidad/organización o su ubicación geográfica.
- **Second-Level Domains:** nodos a dos saltos de la raíz. Indican el nombre de una organización (`google`, `upc`, `wikipedia`...).

## 9. Tipos de TLD

| Tipo | Descripción | Ejemplos |
|---|---|---|
| **TLD genérico** | Dominios de propósito general | `.com`, `.org`, `.net`, `.edu`, `.gov`, `.mil` |
| **sTLD (Sponsored TLD)** | Gestionados por organizaciones privadas/agencias que representan a una comunidad específica | `.aero`, `.museum`, `.travel`, `.jobs`, `.mobi` |
| **Nuevos gTLD** | TLD genéricos más recientes | `.app`, `.shop`, `.blog`, `.online`, `.tech`, `.xyz`, `.club` |
| **ccTLD (Country Code TLD)** | Un país, dos letras según ISO-3166 | `.es`, `.fr`, `.mx`, `.uk`, `.de`, `.jp` |
| **Infraestructura** | Reservado para tareas técnicas de Internet | `.arpa` (único) |

> **ICANN** es la entidad que gestiona los dominios a nivel mundial y reconoce más de **1.500 TLD** de primer nivel activos.

## 10. Dominios y subdominios

- Un dominio es un **sub-árbol** del espacio de nombres DNS: todo el conjunto de nodos hijos/descendientes de un nodo "padre".
- Un dominio es **subdominio** de otro cuando el primero forma parte del segundo.
- Ejemplo: `.edu` hace referencia a todo el árbol que "cuelga" del nodo `.edu`.
  - Bajo `.edu` están, por ejemplo, `ub.edu`, `uab.edu` — no puede haber dos hijos con el mismo nombre bajo un mismo padre (por eso la Universitat Autònoma de Barcelona usa `uab.cat`, no `uab.edu`).
  - `upc.edu` es un sub-dominio de `.edu`.
  - `fib.upc.edu` engloba todos los nodos por debajo de `fib.upc.edu` y es sub-dominio de `upc.edu` y de `.edu`.
  - `gia.fib.upc.edu` pertenecería, a su vez, a todos los dominios anteriores.

## 12. Tipos de registros DNS (Resource Records)

Los registros DNS son cadenas que indican ciertas acciones al servidor DNS. Los principales tipos son: **A, AAAA, CNAME, NS, SOA, MX**.

### A / AAAA
- **A:** referencia la **IPv4** de un servidor → devuelve una dirección de **32 bits**.
- **AAAA:** referencia la **IPv6** de un servidor → devuelve una dirección de **128 bits**.

### CNAME (Canonical Name)
- Es un **alias** de un dominio: apunta desde un dominio alias a un dominio "canónico".
- Se usa para asociar nuevos subdominios con dominios que ya tienen un registro A.
- Un CNAME siempre debe apuntar a **otro dominio**, nunca directamente a una IP.
- **Analogía:** buscar a un delincuente donde cada pista apunta a otra pista, hasta llegar al sujeto (registro A final).
- Ejemplo: `blog.smx.es` tiene un CNAME con valor `smx.es`. Al consultar `blog.smx.es`, en realidad se busca `smx.es`, que devuelve su IP mediante su registro A. `smx.es` es el nombre canónico de `blog.smx.es`.

### MX (Mail Exchange)
- Lista de servidores de intercambio de correo para el dominio.
- Especifica los servidores responsables de aceptar el correo electrónico enviado a ese dominio.
- Necesario para recibir correo a través del propio dominio.
- Apunta a un registro **A o AAAA** que identifica la IP del/de los servidor(es) de correo.

### SOA (Start of Authority)
- Marca el **inicio de una zona de autoridad**.
- Especifica el **servidor de nombres primario** (fuente autoritativa de la zona) y es responsable del funcionamiento general del dominio.
- Incluye el correo del **webmaster/administrador**.
- Contiene: servidor de nombre primario, correo del administrador de la zona, número de serie de la zona.

### NS (Name Server)
- Identifica los **servidores de nombres** de un dominio.
- Debe estar en el archivo de zona al añadir un nuevo dominio, y configurarse **antes** que cualquier otro registro de ese dominio.
- Indica qué servidores de nombres se usan para resolver el dominio (delega la zona a esos servidores autoritativos).

### Estructura general de un Resource Record (RR)

```
<NAME>   <TTL>   <CLASS>   <TYPE>   <RDATA>
```

| Campo | Descripción |
|---|---|
| **NAME** | Nombre de dominio al que pertenece el registro (ej: `www.kirby.com`) |
| **TTL** | Tiempo de vida en caché, en segundos |
| **CLASS** | Casi siempre `IN` (Internet) |
| **TYPE** | Tipo de registro (A, AAAA, MX, CNAME...) |
| **RDATA** | Valor de los datos (una IP, un alias, etc.) |

## 13. DNS primario y secundario

### DNS primario
- Guarda en su propia base de datos la información de una zona determinada del espacio de nombres.
- Cada zona debe disponer de **al menos un servidor de nombres primario**.
- Suele implementarse como un **clúster** (maestro + esclavos) con datos de zona idénticos, aumentando la redundancia, la seguridad ante caídas y la disponibilidad.

### DNS secundario
- La información **no procede de sus propios archivos de zona**, sino de otros servidores → actúa como servidor **secundario/esclavo**.
- Ocurre cuando un servidor no puede resolver una petición con su propia base de datos y recurre a otro servidor (**resolución recursiva**).
- Los datos se guardan temporalmente en **caché local** para peticiones futuras.
- Como las entradas de zona pueden cambiar, la información de los servidores secundarios **no se considera tan segura/fiable** como la del primario.

## 14. Resumen rápido

- El DNS traduce **nombres ↔ IPs**, es jerárquico y distribuido, y usa el **puerto 53** (UDP/TCP).
- La resolución involucra **resolver → raíz → TLD → autoritativo**.
- Consultas **recursivas** (respuesta garantizada) vs. **iterativas** (respuesta parcial o referencia).
- Registros clave: **A/AAAA** (IP), **CNAME** (alias), **MX** (correo), **NS** (servidores de nombres), **SOA** (autoridad de zona).
- **DNS primario** = fuente original de la zona; **DNS secundario** = réplica/caché de esa información.
