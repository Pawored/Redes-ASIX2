# DNS — Seguridad

> Apuntes basados en la presentación *1.2-DNS-seguridad1.pptx*

## 1. Problemas de seguridad en el DNS

El DNS no se diseñó pensando en la seguridad (se creó cuando solo universidades y centros de investigación tenían acceso a Internet), por lo que es vulnerable a varios tipos de ataque:

- **Pharming**
- **DNS Hijacking** (secuestro de DNS)
- **DNS Spoofing** (suplantación / envenenamiento de DNS)
- Como protección: **DNSSEC** (extensiones de seguridad para el DNS)

## 2. Pharming

Los atacantes redireccionan un nombre de dominio a una IP distinta **aunque el usuario introduzca la dirección correcta**.

| Tipo | Descripción |
|---|---|
| **Local** | El atacante infecta el dispositivo con malware que modifica la configuración DNS local (p. ej. el archivo `hosts`), redirigiendo al usuario a sitios fraudulentos aunque escriba la URL correcta. |
| **DNS** | El atacante ataca directamente a los servidores DNS, pudiendo redirigir el tráfico de miles de usuarios a sitios maliciosos sin tener que comprometer cada dispositivo individualmente. |

## 3. DNS Hijacking (secuestro de DNS)

Técnica que **redirige el tráfico** que debería ir a un dominio legítimo hacia un servidor controlado por el atacante.

### Objetivos habituales
- Mostrar páginas falsas (**phishing**).
- Inyectar publicidad.
- Capturar credenciales.
- Distribuir malware.

### Funcionamiento
1. El atacante resuelve incorrectamente las consultas DNS, redirigiendo el tráfico a un sitio malicioso.
2. Cuando el navegador resuelve la URL, un servidor falso responde con una IP falsa, perteneciente a un sitio malicioso.
3. El usuario introduce datos confidenciales en ese sitio falso, y el atacante los roba.

### Modalidades (según el nivel de acceso/privilegios del atacante)

| Modalidad | Alcance | Dificultad | Responsabilidad |
|---|---|---|---|
| **Secuestro local** | Solo el dispositivo cuya configuración de resolución fue modificada | Fácil de realizar | Del usuario |
| **Secuestro del router** | Todos los equipos conectados a esa red | Fácil de realizar | Del usuario |
| **Secuestro del servidor DNS** (a nivel de Internet) | Potencialmente global | Complicado — depende de terceros | De la seguridad del proveedor/servidor |

#### Secuestro local
- Afecta solo al equipo cuya configuración de resolución de direcciones fue modificada.
- Suele deberse a **malware, troyanos** y similares.
- Causa típica: descarga de apps desde páginas no oficiales; las técnicas más comunes usadas por los ciberdelincuentes son el **phishing** y el **pharming**.

#### Secuestro del router
- Afecta a **todos los equipos de la red**.
- El atacante desvía las peticiones que recibe el router hacia Internet a un servidor bajo su control, redirigiendo el tráfico a páginas fraudulentas o diseñadas para robar información.
- Suele relacionarse con **contraseñas por defecto** en routers y redes WiFi sin seguridad o con seguridad débil.

#### Secuestro del servidor DNS
- Ataque contra el servidor DNS que atiende peticiones a nivel global en Internet.
- Los equipos locales no se ven directamente afectados, pero pueden ser redirigidos a páginas fraudulentas (phishing) o con mucha publicidad (pharming).
- Se trata de ataques muy concretos y elaborados, poco frecuentes: la seguridad de estos servidores es muy alta y las penas legales son severas, lo cual disuade a la mayoría de atacantes.
- Aun así, conviene estar atentos al comportamiento del navegador e implementar medidas adicionales de terceros.

### Protección frente al DNS Hijacking

- Instalar **antivirus, antimalware y antiphishing**.
- Tener **control del router**.
- Poner el router del ISP en **modo puente** y usar un DNS propio, para evitar que el ISP redirija a páginas con publicidad cuando una web da error; revisar periódicamente que el DNS configurado en el router no haya sido modificado.
- **Actualizar el firmware y el sistema operativo** del router, para evitar vulnerabilidades.
- **Cambiar las credenciales por defecto** del router, manteniendo una política de contraseñas robustas.
- Usar **servidores DNS seguros** (DNS sobre HTTPS o DNS sobre TLS), que cifran las peticiones y dificultan la suplantación.
- **Descargar aplicaciones solo desde páginas oficiales** (con certificado HTTPS).
- **No hacer clic en enlaces extraños** ni acceder a páginas dudosas.

### ¿Cómo saber si soy víctima de DNS Hijacking?

- **Comprobar el archivo `hosts`** del equipo: revisar las entradas que contiene y ver si la IP y el nombre de dominio son coherentes entre sí.
- **Comprobar los ajustes DNS del router**: acceder al apartado **WAN** y verificar que las IP configuradas coinciden con las proporcionadas por el proveedor (si no coinciden, cambiarlas y también cambiar la contraseña del router para evitar que el atacante vuelva a modificarlas).
- Existen **servicios de verificación** de nombres de dominio en la red que, aunque no siempre son fiables ni concluyentes, pueden ayudar en algunos casos.

## 4. DNS Spoofing (suplantación / envenenamiento de caché)

- Consiste en **introducir información falsa en una caché DNS**, de modo que las consultas devuelvan una respuesta incorrecta y dirijan al usuario a sitios web equivocados.
- Los **resolvers de DNS no pueden verificar** los datos que almacenan en su caché.
- La información falsa permanece en caché hasta que **caduca el TTL** o se elimina manualmente.
- El atacante envenena la caché **haciéndose pasar por un servidor DNS**: realiza una solicitud a un resolver y falsifica la respuesta antes de que llegue la respuesta legítima.
- Esto es posible porque el DNS usa **UDP** (no TCP) y porque no hay verificación de la información.

> Referencia: https://www.cloudflare.com/es-es/learning/dns/dns-cache-poisoning

### Por qué el uso de UDP hace vulnerable al DNS

- El DNS se diseñó en los inicios de Internet, cuando no había motivo para prever la difusión de información falsa.
- Las solicitudes y respuestas DNS usan **UDP**, que **no garantiza** que una conexión esté abierta ni que el destinatario esté listo para recibir → vulnerable a la **falsificación (spoofing)**.
- Un atacante puede enviar un mensaje UDP falsificando los datos de la cabecera para que parezca la respuesta de un servidor legítimo.
- Si el resolver recibe una respuesta falsificada, **la acepta y la cachea**, ya que no puede verificar su procedencia ni su exactitud.

### Dificultad real del ataque

Aunque el proceso de caché tiene vulnerabilidades, envenenar el DNS no es trivial:

- El resolver hace la consulta real al servidor de nombres autoritativo; el atacante solo dispone de **unos milisegundos** para enviar la respuesta falsa antes de que llegue la real.
- El atacante necesita **acertar o adivinar** varios factores:
  - Qué consultas DNS **no están en caché** en el resolver objetivo.
  - Qué **puerto** usa el resolver (antes era fijo, ahora es **aleatorio** en cada consulta).
  - El **número de ID** de la solicitud.
  - A qué **servidor de nombres autoritativo** irá dirigida la consulta.

## 5. DNSSEC (Domain Name System Security Extensions)

**Capa de seguridad adicional** al protocolo DNS, pensada para solucionar el problema del envenenamiento de caché.

- Verifica la **integridad** de los datos DNS y su **origen**.
- El DNS original no incluía ningún mecanismo de verificación → de ahí la posibilidad del envenenamiento.
- Al igual que **TLS/SSL**, DNSSEC usa **criptografía de clave pública** (asimétrica) para firmar digitalmente la información y así verificarla/autenticarla.
- Las extensiones DNSSEC se publicaron en **2005**, pero su adopción sigue siendo limitada, por lo que el DNS sigue siendo vulnerable en la práctica.

### Caso real (histórico)

- Los servidores de correo usan el DNS para enrutar los mensajes, por lo que también son vulnerables a problemas de seguridad del DNS.
- En **septiembre de 2014**, investigadores de la **Carnegie Mellon University (CMU)** descubrieron correos dirigidos a Yahoo!, Hotmail y Gmail que en realidad se enrutaban a través de **servidores de correo no autorizados**.
- Los atacantes explotaban una vulnerabilidad de **décadas de antigüedad** en el DNS: no comprueba las credenciales antes de aceptar una respuesta.
- La solución propuesta es **DNSSEC**, que añade una capa de confianza mediante autenticación.

### Ejemplo de funcionamiento (Cloudflare)

Al buscar `blog.cloudflare.com`:

1. El resolver DNS busca el dominio.
2. Los **servidores de nombres raíz** ayudan a verificar `.com`.
3. Los **servidores de nombres `.com`** ayudan al resolver a verificar los registros devueltos por Cloudflare.
4. **Cloudflare** ayuda a verificar los registros devueltos para `blog`.
5. La información publicada por la raíz pasa por un procedimiento de seguridad exhaustivo, incluida la **ceremonia de firma de la zona raíz**.

### ¿Qué aporta DNSSEC?

- Es **fundamental** para protegerse frente al secuestro de DNS.
- Protege **firmando digitalmente** los datos en **cada nivel** del proceso de búsqueda DNS, garantizando una resolución segura.
- Autentica el **origen** de los datos y confirma que **no han sido manipulados** en el camino.
- Su implementación **no es sencilla**: muchos registradores no la tienen habilitada en sus servidores DNS, o no la soportan para todos los TLD.
- Usa **criptografía asimétrica** (de clave pública): una clave **pública**, de dominio público, y una clave **privada**, que solo conoce su propietario.

### Cómo funciona técnicamente

- DNSSEC añade **firmas criptográficas** a los registros DNS existentes.
- Estas firmas se almacenan en los servidores de nombres junto a los registros habituales (A, AAAA, MX, CNAME, etc.).
- Al comprobar la firma asociada a un registro, se puede verificar que proviene realmente de su **servidor de nombres autoritativo** y que **no ha sido alterado** en el camino (a diferencia de los registros falsos inyectados en ataques de intermediario / man-in-the-middle).
- El proceso general:
  1. El usuario busca un dominio con DNSSEC habilitado.
  2. Se envía la IP resuelta **junto con las firmas** de las claves de los distintos servidores DNS consultados.
  3. Si las firmas **coinciden entre sí**, la cadena de confianza está intacta y se permite el acceso al sitio.
  4. Si **no coinciden**, la cadena de confianza se ha roto, la consulta no se valida y no es seguro acceder al sitio.

### Nuevos tipos de registro que añade DNSSEC

| Registro | Función |
|---|---|
| **RRSIG** | Contiene una firma criptográfica. |
| **DNSKEY** | Contiene una clave de firma pública. |
| **DS** | Contiene el hash de un registro DNSKEY. |
| **NSEC / NSEC3** | Para la negación explícita de la existencia de un registro DNS. |
| **CDNSKEY / CDS** | Usados por una zona secundaria para solicitar actualizaciones de registros DS en la zona principal. |

## 6. Resumen rápido

| Ataque | Idea clave | Defensa principal |
|---|---|---|
| **Pharming** | Redirige el dominio a otra IP aunque la URL sea correcta (local o vía servidor DNS) | Antimalware, revisar `hosts`, DNS seguros |
| **DNS Hijacking** | Secuestra la resolución (local, router o servidor) para redirigir tráfico | Antivirus, asegurar router, DNS sobre HTTPS/TLS, credenciales robustas |
| **DNS Spoofing / envenenamiento de caché** | Se inyecta una respuesta falsa en la caché aprovechando que DNS usa UDP sin verificación | **DNSSEC** (firma criptográfica del origen e integridad de los datos) |
